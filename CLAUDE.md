# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
A small Ubuntu desktop app (Python 3, GTK 3 via PyGObject). It polls every Vikunja project through the REST API v2 and shows each project as a narrow tab at the right screen edge; hovering a tab reveals that project's unfinished tasks as borderless popup cards. Optionally it reads new emails over IMAP and new GitHub items (issues/PRs assigned to the user, new comments on the user's PRs), asks an opencode AI model what to do about each one, and shows the proposed task changes and replies in an "Inbox" tab for the user to confirm. There are no tests, no linter config and no build step.

## Commands
- Run from the source tree: `.venv/bin/python app.py`
  - The local `.venv` was created with `--system-site-packages` because `gi` (PyGObject), GTK and gtk-layer-shell come from apt (`python3-gi gir1.2-gtk-3.0`, plus `gir1.2-gtklayershell-0.1` on non-GNOME desktops), not pip. pip only installs `requests`.
  - If you recreate the venv, use `python3 -m venv --system-site-packages .venv && .venv/bin/pip install -r requirements.txt`.
- Install system-wide for the user: `./install.sh`. It runs apt, copies the `.py` files into `~/.local/share/vikunja-popups/` with its own venv, and installs the systemd user unit (`WantedBy=graphical-session.target`, so the display environment is available). It can be re-run: it only calls `sudo apt` for missing packages, reuses the venv unless the Python version changed, keeps the config, and restarts the service if it's active. Run it as your normal user, not root.
- Settings app: `.venv/bin/python settings.py`. `install.sh` also registers it in the application menu as "Vikunja Popups Settings" by filling `@APP_DIR@` in `vikunja-popups-settings.desktop.in` and writing the result to `~/.local/share/applications/` (`.desktop` files need an absolute `Exec` path).
- Logs: `journalctl --user -u vikunja-popups.service -f`
- Uninstall: `./uninstall.sh` (keeps the config).

## Configuration
- The app always reads `$XDG_CONFIG_HOME/vikunja-popups/config.json` (default `~/.config/...`), **not** the `config.json` in this directory. `load_config()` creates a placeholder there if the file is missing.
- `VIKUNJA_TOKEN` in the environment overrides `token`.
- `config.py` clamps values (`refresh_seconds` >= 10, `popup_width` >= 260, `max_visible` >= 1) and rejects the placeholder `base_url`. There is no project setting: every project the token can see gets a tab.
- `VikunjaClient` appends `/api/v2` to `base_url` when it's missing.
- `config.example.json` and `config.json` in this directory hold a real base URL and API token. `install.sh` copies `config.example.json` to the user config. Treat both as secrets.
- `ai_model` is an opencode model id (`provider/model`, empty = none). It drives the email assistant (see Architecture). `opencode_models.py` (no GTK) finds the opencode binary (`PATH`, then `~/.opencode/bin/opencode`, because menu- and systemd-started processes lack the shell's `PATH`) and `list_models()` parses `opencode models`. The settings app fills its "AI model" combo box from it in a thread; the combo has an entry so an id can be typed when opencode is unavailable, and the value is not validated against the list.
- `email` is a nested object holding exactly one account (`address`, `username`, `password`, `imap_*`, `smtp_*`; security is `ssl` / `starttls` / `none`), exposed as `Config.email` (`EmailConfig`, built by `email_config_from()`). `normalize_email()` in `config.py` fills defaults and replaces bad values instead of raising, so a broken email section never stops the popups; both `load_config()` and the settings app use it. The settings app edits it on the "Email" notebook page; "Test login" calls `mail_client.test_login()` in a thread. The password sits in the mode-0600 config file like the token.
- `github` is a nested object holding one GitHub account (`username`, `token` = personal access token, `api_url`, default `https://api.github.com`, for GitHub Enterprise), exposed as `Config.github` (`GitHubConfig`, built by `github_config_from()`); `normalize_github()` is lenient like `normalize_email()`. It drives the GitHub assistant (see Architecture). The settings app edits it on the "GitHub" page; `username` is a read-only label: saving clears it when token or `api_url` changed, then `_fill_github_username()` (also run at startup) fetches it with `github_client.get_login()` in a thread and saves it, ignoring the answer if another token was saved meanwhile; "Test login" calls `github_client.test_login()` (`GET /user`, no GTK) in a thread. "Create token" opens `github_client.token_page_url()` (the fine-grained token page, on the Enterprise host when `api_url` points there) with `Gtk.show_uri_on_window`.
- Adding a config key means updating the `Config` dataclass, `EXAMPLE` and `load_config()` in `config.py`, the form in `settings.py` (`NUMBER_FIELDS` / `SWITCH_FIELDS`), plus `config.example.json` and the README.
- `settings.py` is a separate process with an ordinary decorated `Gtk.Window` (no XWayland forcing, no `setup_popup_window`). It uses `read_raw_config()` / `save_raw_config()` from `config.py` because `load_config()` raises on an unconfigured file; saving updates the dict it read (unknown keys survive), writes atomically with mode 0600 and restarts `vikunja-popups.service` if it is active. "Test connection" calls `VikunjaClient.get_projects()` in a thread with the unsaved form values. The "Stop app" / "Start app" button runs `systemctl --user stop|start` on the service (its label follows `is-active`); stopping lasts until the next login. `GLib.set_prgname("vikunja-popups-settings")` must match the `.desktop` file name so GNOME shows the right name and icon. The icon is `vikunja-popups-settings.svg`; `install.sh` puts it into `~/.local/share/icons/hicolor/scalable/apps/` (the `.desktop` file references it by name) and the window falls back to the file next to `settings.py` when the theme has no such icon.

## Architecture
- `vikunja_client.py`: a `requests.Session` with a Bearer token. `_paginated()` walks a collection endpoint following v2 pagination (`items` / `total_pages`) and also accepts a bare-list response for older servers; `get_projects()` and `get_project_tasks()` are built on it. `get_projects()` drops archived projects and the server's pseudo projects ("Favorites", "My Open Tasks"), which come back with negative ids and reject new tasks. `get_project_tasks()` filters out `done` tasks on the client side. Every HTTP error is wrapped in `VikunjaError`, using the API's `detail`/`message` text when there is one. `VikunjaProject` and `VikunjaTask` are frozen dataclasses built by `from_api()`.
- `vikunja_client.py` also has `create_task()` (title plus optional HTML description, priority, due date), `get_task()`, `update_task()` (`PATCH /tasks/{id}` as `application/merge-patch+json`, only the given fields), `add_comment()` (`POST /tasks/{id}/comments`) and `text_to_html()`, because Vikunja stores descriptions and comments as HTML. The server's API description is at `/api/v2/openapi.json`.
- `mail_client.py` (no GTK): `connect_imap()` / `connect_smtp()` return logged-in connections; `fetch_new_messages(account, since, seen_keys, limit)` selects INBOX **read-only**, searches `SINCE` one day before `since` (IMAP dates only), then filters by `INTERNALDATE` >= `since` and skips keys in `seen_keys`, oldest first, bodies via `BODY.PEEK[]` so nothing gets marked as read. A message key is `"<UIDVALIDITY>:<UID>"`. IMAP month names are hard-coded because GTK sets the locale and `%b` would be localized. `send_reply()` answers to `Reply-To`/`From` with `In-Reply-To`/`References` and the original quoted; no copy to Sent.
- `ai_mail.py` (no GTK): `analyze()` builds the prompt (projects, open tasks with shortened plain-text descriptions, the email marked as untrusted), runs `opencode run --standalone --agent vikunja-popups-mail -m <model>` with the prompt on **stdin**, in `$XDG_STATE_HOME/vikunja-popups/opencode/`, whose `opencode.json` (`ensure_agent()`) defines that agent with `"permission": "deny"`, so the model has no tools. Three opencode details matter: `--standalone` because the shared background service caches project config per directory (a new or changed `opencode.json` gave "Agent not found"); `PWD` must be set in the child's env because opencode locates the project through `$PWD`, not the real cwd; and no `steps` limit, because opencode enforces it with a trailing assistant message that vLLM providers (the `ki-toolbox/*-local` models) reject. `parse_answer()` takes the outermost `{...}` of the answer and drops actions with unknown task ids or empty values; an unreadable answer becomes a proposal with `error` set and no actions. Action types: `create_task` (no project: new tasks always go to the `TODO_PROJECT` ("ToDo") project, which `_run_action` looks up or creates with `VikunjaClient.ensure_project()` when it executes; a `project_id` in older stored proposals is ignored), `update_task` (`changes`: `title`, `priority`, `due_date`, `done`, `append_description`), `add_comment`, `reply`.
- `github_client.py` (no GTK): `test_login()` / `get_login()` call `GET /user`; `token_page_url()` builds the token page link. `GitHubClient` (a `requests.Session`) follows `Link` pagination up to `MAX_PAGES` and uses the search API: `assigned(login)` = open issues/PRs with `assignee:<login>`; `new_pr_comments(login, since, until)` = PRs with `author:<login>` updated since `since`, then their issue comments, review comments and reviews (approved / changes requested / with text) by others created in `[since, until)`, one `GitHubItem` per PR whose key ends with the newest comment id. Search, not the notifications API, because fine-grained tokens cannot read notifications.
- `ai_mail.py` also handles GitHub: `analyze_github()` uses `GITHUB_PROMPT` (existing task → `add_comment`/`update_task`, else one `create_task`, link included) and `parse_answer(..., allowed=GITHUB_ACTIONS)` drops `reply`. `_context()` builds the project/task lines both prompts share.
- `app.py`, class `VikunjaPopupApp`, threading model:
  - A `GLib.timeout_add_seconds` timer calls `refresh()`, which starts a daemon thread (`_fetch_worker`). A `self.fetching` flag keeps fetches from overlapping.
  - The worker never touches GTK. It fetches the project list, then the tasks of each project in turn, and hands results back with `GLib.idle_add(_apply_projects | _show_error)`. Keep all widget code on the main loop. A project whose tasks fail to load is left out of the result dict (its tab keeps the previous tasks) and its error is collected; only a failure of the project list itself aborts the refresh.
  - `_apply_projects` rebuilds `self.views` (an ordered `{project_id: ProjectView}`) in API order, creating views for new projects, destroying views for projects that are gone, and then calls `_place_tabs()`.
  - `ProjectView` owns one project's `TaskTab`, `TaskPanel`, task list, dismissals and hover state, so projects never interfere with each other. `ProjectView.render()` sorts with the module-level `sort_key()` (priority descending, then tasks with a due date, then due date, then id), skips dismissed ids, sets `self.visible` (capped at `max_visible`, ignoring the filter) which drives the tab color and whether the panel may open, and fills the panel with the tasks matching the filter, capped at `max_visible`.
  - Email assistant (`_start_mail_check`, called from `_apply_projects`, at most every `refresh_seconds / 2` because dismissing/creating also refreshes; only with `ai_model` and an IMAP host): state lives in `config.STATE_FILE` (`$XDG_STATE_HOME/vikunja-popups/state.json`, 0600) as `mail_since` (epoch of the last handled email), `mail_seen` (keys handled at exactly that second) and `proposals`. Without `mail_since` it only stores `time.time()`. `_mail_worker` fetches up to `MAIL_BATCH` emails and calls `ai_mail.analyze()` for each with a snapshot of projects/tasks taken on the main thread; `_on_mail_analyzed` (main thread, so all state writes happen there) advances `mail_since` per email and stores a proposal when it has actions or an error. An exception aborts the batch without advancing, so the email is retried on the next refresh; `_on_mail_done` shows each distinct error once. Executing runs the ticked, edited actions in a thread (`_run_action`); failed ones stay on the proposal with the error, unticked ones are dropped.
  - GitHub assistant (`_start_github_check`, same throttle, with `ai_model` and a GitHub token; independent of the mail check via `github_busy`): state keys `github_assigned` (refs `owner/repo#n` of assigned items already handled, pruned to the still-open ones after each successful check), `github_since` (start of the comment window) and `github_seen` (comment item keys handled within the window). The first run only records what is assigned and the time. `_github_worker` hands at most `GITHUB_BATCH` items to the AI and only advances `github_since` when none were left over; `_on_github_analyzed` marks each item and stores a proposal (`id` = item key, `message` = `{"source": "github", "subject", "sender", "timestamp", "url"}`).
  - Dismissals live only in memory (`ProjectView.dismissed`). They are pruned to ids still in that project's active list, so a task that gets completed and later reopened shows up again. Dismissing a task re-renders from `self.tasks` (so the next task fills the slot) and triggers a refresh.
- Windows: one `TaskTab` per project sits flush at the right screen edge, stacked downwards (`_place_tabs` accumulates each tab's real height plus `TAB_GAP`). A tab is `TAB_WIDTH` wide and at least `TAB_HEIGHT` tall; its label is rotated 270° so the project name reads downwards, and the tab grows with it. GTK cannot ellipsize a rotated label, so `TaskTab.set_heading()` shortens names past `TAB_MAX_CHARS` itself. The tab is colored by the project's highest priority. Each project's cards (`TaskCard`, an input-only `Gtk.EventBox`) live in **one** `TaskPanel` window, hidden by default and placed directly left of the tab column (`right=TAB_WIDTH`, `top=0`, so every project's panel opens at the same height regardless of its tab's offset). `MessagePopup` is an error toast that closes itself after 8 s. Every window is set up by `setup_popup_window()` (transparent RGBA window, `.popup-window` class, NOTIFICATION hint or layer-shell) and positioned by `place_popup_window(window, config, top=0, right=None)`, which must be called **after** `show_all()` because GTK reports a placeholder size before that. The panel re-places itself in `size-allocate` so it stays right-aligned as cards are added or removed.
- `FilterCard` (an entry at the top of the panel) filters cards by case-insensitive title substring; typing calls the owning `ProjectView.render()` and Escape clears it. It is created once in `TaskPanel.__init__`; `set_tasks()` only rebuilds the `self.cards` box. The panel uses `setup_popup_window(..., focusable=True)` (accept focus but not on map, UTILITY hint instead of NOTIFICATION, layer-shell `ON_DEMAND`), because Mutter never focuses NOTIFICATION windows. A click on the entry calls `present_with_time`. The panel doesn't auto-hide while the entry has focus, and schedules the hide on `focus-out-event`.
- New task: a left click on a tab (`_on_tab_click`) opens `NewTaskDialog` for **that** project, a centered, focusable single-entry window (DIALOG hint, `present_with_time` with the click timestamp so Mutter grants focus). Only one dialog exists at a time; clicking another tab destroys the open one first. Submitting runs `VikunjaClient.create_task()` (`POST /projects/{id}/tasks` with `{"title"}`) in a thread. On success the dialog closes and `_refresh_soon()` refetches, retrying while a fetch is already running. On failure the error is shown inside the dialog. Escape closes it. The tab stays visible with 0 tasks so this always works.
- `HoverView` is the base of `ProjectView` and `AiView`: a tab, a `PanelWindow` (base of `TaskPanel` and `ProposalPanel`: focusable popup window placed left of the tab column, re-placed on `size-allocate`), hover state and the hide timer. Subclasses override `can_show()` (panel may open) and `keep_open()` (stay open after the pointer left: the filter has focus / the proposal panel is the active window). `AiView` is the purple "Inbox · N" tab, placed first and hidden while there are no proposals. `ProposalPanel` keeps cards by proposal id (`by_id`) and only adds/removes cards, so edits survive new arrivals; `replace()` swaps one card after a partial failure. It scrolls when taller than the work area. `ProposalCard` shows one email or GitHub item (the title links to `message["url"]` when set): a `CheckButton` per action, an `Entry`/`TextView` for editable texts (`focus_on_click()` calls `present_with_time` so the WM gives the panel focus), "Execute selected" and `×` (discard).
- Hover logic (`VikunjaPopupApp._on_enter` / `_on_leave`, per view, over `_all_views()` = AI view plus project views): entering a tab shows its panel and force-hides every other panel, so only one is ever open. `HoverView.inside` tracks whether the pointer is in that project's tab or panel, and the panel hides `HIDE_DELAY_MS` (300 ms) after it has left both. Leave events with `detail == INFERIOR` (pointer moved onto a child's input window, such as a button or card) must be ignored. `_apply_projects` rebuilds only each panel's cards and never destroys the windows of projects that still exist, so the hover state survives refreshes. Styling is the `CSS` bytes constant plus style classes; priority colors are shared by `.task-popup.priority-N` and `.task-tab.priority-N`.
- Display backends (decided at import time in `app.py`, before `Gtk` is imported):
  - **GNOME / no gtk-layer-shell** (the author's setup: Ubuntu GNOME on Wayland): Mutter doesn't implement wlr-layer-shell and ignores window positioning on Wayland, so the app sets `GDK_BACKEND=x11` and runs through XWayland. Windows get the `NOTIFICATION` type hint (above other windows, not in Alt+Tab) and are `move()`d relative to `monitor.get_workarea()`, which excludes the top bar.
  - **Other wlroots-style compositors with gtk-layer-shell installed**: OVERLAY layer anchored top/right, with the stack offset set as the top margin.

## Known quirks (current code)
- Checking the layout: `xwininfo -root -tree | grep '"app.py"'` while the app runs. On a scaled display it reports device pixels (for example 2x logical).
- Dates are shown in local time as `%d.%m.%Y %H:%M` (`format_due_date`).
